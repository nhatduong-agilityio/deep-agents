## Concepts covered

- **Dockerfile baking vs runtime override:** `langgraphjs dockerfile` bakes `LANGGRAPH_HTTP` (including CORS config from `langgraph.json`) as an ENV in the image at build time. For production, `docker-compose.yml` overrides this ENV at container start via `LANGGRAPH_HTTP: '{"cors":{"allow_origins":["${LANGGRAPH_ALLOW_ORIGIN}"]}}'`. This means the dev CORS origins (`localhost:5173`) are in the image but replaced in production — no rebuild needed to change CORS.

- **Corepack pnpm resolution in Docker:** Corepack reads the `packageManager` field in `package.json` to pin the pnpm version used inside the Docker build. Without that field, it downloads the latest pnpm at build time, which failed in the container environment. The fix is `"packageManager": "pnpm@11.22.0"` matching the developer's installed version.

- **Production persistence requirements:** The `langchain/langgraphjs-api:24` production image requires external PostgreSQL (pgvector extension) for durable thread-state checkpointing and Redis for SSE pub/sub fan-out. The dev server uses an in-process `InMemorySaver` backed by a JSON file, which does not survive container restarts. These are injected via `POSTGRES_URI` and `REDIS_URI` env vars.

- **`.dockerignore` and secrets:** `.env` must be in `.dockerignore` so secrets are never copied into the image layer, even accidentally. `.env.example` is explicitly allowed (it contains no real values). The pattern `.env.*` + `!.env.example` achieves this.

- **`VITE_*` vars are public:** Any value in a `VITE_*` env var is baked into the JS bundle at build time and visible in the browser's DevTools. Only `VITE_API_URL` (a URL, not a secret) is acceptable. API keys must remain server-side only.

## Decisions and reasons

**Merging into existing `docker-compose.yml` rather than replacing:** The project already had a `docker-compose.yml` for the LLM Guard sidecar (behind `profiles: [guardrails]`). Replacing it would have broken that existing optional feature. Merging added the three LangGraph services while preserving the LLM Guard service unchanged.

**Runtime CORS override via `LANGGRAPH_HTTP`:** Since the Dockerfile is generated by the CLI and bakes CORS at build time, the production CORS must be set as a runtime override in docker-compose rather than being in `langgraph.json`. A separate `LANGGRAPH_ALLOW_ORIGIN` env var keeps this configurable without rebuilding the image.

**DDR-016 Option A (custom auth):** Applied from DDR-016. The `apps/api/src/auth.ts` duck-typed `~handlerCache` pattern is already in `langgraph.json` as `auth.path`. `docs/deploy.md` documents the Bearer token header requirement for direct API calls.

## Gotchas / lessons learned

- **Corepack kills the build silently.** Without `"packageManager"` in `package.json`, the Docker build picked up the _latest_ pnpm from Corepack's network cache, which wasn't available in the container environment. The error looked like a missing module rather than a version mismatch. Always pin `"packageManager"` when using pnpm in Docker.
- **`langgraphjs dockerfile --add-docker-compose` requires a running Docker daemon.** The CLI calls `docker inspect` to find the compose template. If Docker Desktop is not running, the compose generation silently fails (`ExecaError`) even though the Dockerfile itself generates fine. Write docker-compose.yml manually (or from the CLI source) when the daemon isn't available.
- **The baked `LANGGRAPH_HTTP` ENV is the entire HTTP config object, not just CORS.** When overriding at runtime in docker-compose, the full JSON must be provided (not just a `cors` key). The production override `'{"cors":{"allow_origins":["..."]}}' ` is intentionally minimal — it omits the `disable_*` flags, which default to `false`.
- **`apps/web/` must be in `.dockerignore`.** The frontend is deployed separately as a static build; including it in the API image bloats the layer for no benefit and may accidentally expose dev build artifacts.
